Fit make-work-fun on Supabase's free plan

Draft for review, 2026-11-22. Saves about $30/month without leaving Supabase, so we can upgrade again any time.

Problem

The project costs about $30/month: Pro ($25) plus a "Small" server ($15) minus Pro's $10 credit. "Small" is inferred from the database's settings (90 max connections, 512 MB shared buffers); the billing page should confirm it. Usage is tiny (5 people signed in during the last 30 days, 20 signups in 90 days), so the free plan should be enough. Measured on 2026-11-22, three things stop us dropping to free today:

Why storage is so big

Every upload stores the original file as-is: no resizing and no size limit on any of the 5 buckets. The biggest avatar is a 42 MB GIF, and the median daily photo is 3–4 MB. 108 daily photos are HEIC, which most browsers can't display at all. Many files are also unused, left behind when someone changed their avatar or background.

Why downloads are high

All buckets are private, so the app fetches every image through the storage API at full size (supabase.storage.download() in utils/downloadImage.js and a few pages). In the 24 hours to 2026-11-22 there were 339 storage downloads of only 19 distinct files: the homepage and leaderboard re-download the same few full-size avatars. The 139 responses that reported a size totalled 98 MB, which projects to roughly 3–7 GB/month against a 5 GB allowance. Shrinking the images fixes this as a side effect.

Why the leaderboard refresh is a risk

The refresh-leaderboards cron job rebuilds both leaderboard materialized views every 5 minutes, averaging 19.8 s on the current server: about 95 minutes of heavy database work a day. Most ticks change nothing, because few wins arrive. On the free plan's shared-CPU server that could be several times slower and would compete with page loads.

Who this is for

Conrad, who wants to keep make-work-fun alive at near-zero cost while it's quiet and come back to it later. Players are unaffected except that images load faster.

Proposal

Stay on Supabase and change three things. Shrink every image in place, under the same storage key so no database row changes, and delete files nothing uses. Refresh the leaderboards only when wins or profiles changed, plus once an hour for the time-based columns. Add a weekly pg_dump to a private GitHub repo. Then Conrad downgrades to the free plan in the dashboard.

What players see: nothing changes, except images load faster and iPhone HEIC daily photos start displaying. New uploads are resized in the browser before they're sent.

Rejected, so the executor doesn't reverse them

  • New keys (x.webp) and rewriting references. Image paths live in at least eight columns across seven tables and are baked into the leaderboard materialized views. Rewriting all of them is a data migration with many ways to miss one. Overwriting the same key with smaller bytes and the correct Content-Type changes no row. Browsers pick the image format from the bytes, not the file extension, so a .gif key holding animated WebP displays correctly.
  • Moving images to Cloudflare R2. This needs new upload and download code plus URL changes everywhere. It's the fallback if phase 0 shows shrinking can't get under the limit.
  • Leaving Supabase (Neon plus separate auth). Every query and login in the app goes through supabase-js v1, and the sync and refresh rely on pg_cron and pg_net. That's a rewrite to save the same $30.
  • Making the leaderboard query itself faster. all_wins deliberately uses UNION (see AGENTS.md), and changing scoring logic is out of scope. Skipping refreshes that would change nothing gets most of the saving with no risk to scores.
  • Making buckets public and serving from the CDN. Daily photos are private content, and a mixed setup adds a second code path. Smaller files are enough.

Success criteria

  • Total storage under 800 MB (20% headroom), measured with SQL over storage.objects.
  • Every image still in use downloads and decodes after phase 3. A script checks each referenced key, and screenshots of the homepage, leaderboard, a profile, the item shop and a daily photo match before and after.
  • Storage bytes served per day (edge logs) drop by at least 70% from the 2026-11-22 baseline.
  • Leaderboard refreshes drop from 288/day to roughly 24 hourly runs plus one per batch of real changes. A test win posted through /api/wins still shows on the leaderboard within 5 minutes, then gets deleted.
  • The weekly backup workflow runs green, and its dump restores into a throwaway Postgres with matching row counts for success_plan, users and completed_habits.
  • After the downgrade: no pause for 7 days, the Notion sync keeps 0 failures, and the leaderboard API stays under 1 s.

Signs it didn't work: a broken image anywhere, a leaderboard that lags new wins by more than 5 minutes, refresh time over 60 s on the free server, or the project pausing.

Scope

In: shrinking stored images, deleting unused ones (after Conrad approves the list), resizing new uploads in the browser plus bucket size and type limits, refresh-on-change, weekly database backups, the downgrade checklist.

Out:

  • Upgrading supabase-js v1 or Next 12. That's a separate, larger plan, and nothing here needs it.
  • Collapsing the duplicated downloadImage code in pages/player.js and the two pages/embed/player-details*.js files. That's cleanup unrelated to cost, so it goes to the backlog.
  • Backing up storage weekly. After phase 3 it's under 1 GB and phase 1 keeps a full copy; add it later if wanted.
  • Videos (.mp4, 9 files, 53 MB) and SVGs are left untouched.
  • The billing change itself. Conrad does it in the dashboard (phase 7).

Phase 3 · not started

Shrink existing images in place

Files: scripts/storage/shrink.mjs (new), reusing the download and encode code from inventory.mjs

  1. For every used object (from phase 0), read the file from the phase 1 backup, not from storage. Resize to the bucket preset and encode as WebP quality 80. Animated GIF and animated WebP become animated WebP (sharp(…, { animated: true })). HEIC becomes WebP; if sharp on Windows lacks HEIC support, use JPEG through another decoder or leave those files for a follow-up and say so. Skip SVG, MP4, and any file where the result isn't at least 20% smaller.
  2. Overwrite the same key with upload(key, bytes, { upsert: true, contentType, cacheControl: '31536000' }).
  3. Make it safe to stop and rerun. --dry-run prints the plan and the projected totals. A log file records each key's before and after sizes, so a rerun skips finished keys. Work in batches of 50 and stop on the first upload error.
  4. Verify: for every used key, download it, check the bytes decode as an image with sharp().metadata(), and check the stored Content-Type. Then take the before and after screenshots listed under success criteria (homepage, leaderboard, a profile with a GIF avatar, the item shop, a daily photo).
  5. Rollback: re-upload any key from the phase 1 backup. The same script supports --restore <key|all>.

Phase 5 · not started

Refresh leaderboards only when something changed

Files: supabase/migrations/2026MMDD_refresh_leaderboards_on_change.sql (new), supabase/README-cron.md

  1. Before changing anything, snapshot row counts and total EXP per view for leaderboard and leaderboard_season.
  2. Create private.leaderboard_refresh_state(id int primary key, fingerprint bigint, refreshed_at timestamptz) with one row.
  3. Create private.refresh_leaderboards_if_changed(). First, read the change fingerprint: the sum of n_tup_ins + n_tup_upd + n_tup_del from pg_stat_user_tables for every base table the two materialized views read (derive that list from pg_depend and the view definitions, at least success_plan, completed_habits and users). Then REFRESH MATERIALIZED VIEW CONCURRENTLY both views if the fingerprint differs from the stored one, or if date_trunc('hour', now()) is after date_trunc('hour', refreshed_at). The hourly refresh is there because exp_earned_today, exp_earned_week and the season's latest flag depend on the clock. Store the new fingerprint and time afterwards. Counters reset on a database restart, which reads as a change and causes a harmless refresh.
  4. Point the refresh-leaderboards cron job at the function and keep the schedule 2-59/5 * * * *, so a real change still shows within 5 minutes.
  5. Verify: snapshot totals are unchanged; post a test win via /api/wins, see it on the leaderboard within 5 minutes, then delete it. After 24 hours, cron.job_run_details shows most ticks finishing in milliseconds.

Phase 6 · not started · Conrad does two steps

Weekly database backup

Files: .github/workflows/backup.yml in a new private repo (for example conradlin/make-work-fun-backups). Nothing goes into the public repo: workflow artifacts in a public repo can be downloaded by anyone.

  1. Conrad creates the private repo and adds a secret SUPABASE_DB_URL: the session-pooler connection string from Supabase → Connect, using the rotated password. The free plan's direct connection is IPv6-only, and GitHub runners need the pooler.
  2. Workflow: run weekly (Sunday 04:00 UTC) and on manual trigger. Install a pg_dump at least as new as the server (Postgres 15), dump with --format=custom --no-owner, check the exit code, and upload the dump as a workflow artifact with 90-day retention.
  3. Verify a restore: download the artifact, restore into a throwaway postgres:15 Docker container on this PC, and compare row counts for success_plan, users and completed_habits with production. Then delete the container and the local dump. Before starting Docker work, check that no masterforce CI runner is busy.
